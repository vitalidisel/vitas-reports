# PILOT 30 — הפעלה, פריסה ומצב החיבורים

אפליקציה פרטית בעברית (RTL) לפיילוט של 30 יום: משיכת משחקים ויחסים, ניתוח היסטוריה, בדיקת שילובים שעומדים ביעד (10 ₪ → 210 ₪, יחס 21.00) ותיעוד התוצאות. היא חיה בתוך אפליקציית `vitas-reports` הקיימת (Next.js 14, JavaScript, Supabase) תחת הנתיב `/pilot30`, בלי לגעת במסכים הקיימים.

> **מצב נוכחי:** הקוד, המסכים, בסיס הנתונים והמתאמים מוכנים לנקודת החיבור. אין עדיין מפתחות API, אין בסיס נתונים לפיילוט ואין מקור מאומת ליחסי ווינר. לכן ברירת המחדל היא **מצב demo** מפורש עם נתונים פיקטיביים. שום מסך אינו מציג נתוני הדגמה כנתונים חיים.

## הפעלה מקומית

```bash
npm ci
npm test                       # 48 בדיקות: חישוב, זמן, מנוע שילובים, settlement, שירותים, מתאמים, הרשאות
npm run pilot30:demo           # http://localhost:3300/pilot30 — מצב demo (אין צורך במפתחות)
# screenshots + בדיקות רספונסיביות (דורש Chromium; ראה scripts/pilot30/screenshots.mjs)
PILOT30_DEMO_NOW=2026-09-12T07:00:00Z npm run build && PILOT30_DEMO_NOW=2026-09-12T07:00:00Z npm start -- -p 3300
npm run pilot30:screenshots
```

`PILOT30_DEMO_NOW` מקפיא את השעון **במצב demo בלבד**, כדי שאפשר יהיה לבדוק יום מלא (משחקים עתידיים, יחסים טריים) בכל שעה. במצב חי המשתנה מתעלם.

## פריסה (Vercel + Supabase + GitHub Actions)

1. **בסיס נתונים:** הרץ את `supabase/migrations/0001_pilot30.sql` ב-SQL editor של פרויקט ה-Supabase. כל הטבלאות מתחילות ב-`p30_` ואינן מתנגשות בטבלאות הדוחות. RLS מופעל; הכתיבה נעשית רק מהשרת עם service-role.
2. **משתמש יחיד:** צור למשתמש (ויטלי) חשבון ב-Supabase Auth (Invite user), כבה הרשמה פתוחה בהגדרות ה-Auth, והעתק את ה-UUID שלו ל-`OWNER_USER_ID`. כל route בשרת בודק שה-JWT שייך ל-`OWNER_USER_ID`; משתמש אחר מקבל 403 גם אם הצליח להתחבר.
3. **משתני סביבה:** לפי `.env.example`. סודות רק ב-Vercel/מנהל סודות. `.env.example` מכיל placeholders בלבד.
4. **תזמון:** `.github/workflows/pilot30-cron.yml` קורא ל-`/api/pilot30/cron/{discover,odds,lineups,results,reconcile}` עם `CRON_SECRET`. גם `vercel.json` מכיל את אותם crons כגיבוי. כל משימה נעולה (`p30_job_locks`), מתועדת (`p30_sync_runs`) ואידמפוטנטית. **זו תוכנית ליישום — הריצות מופיעות במסך "בריאות המערכת" רק אחרי שהתזמון הופעל בפועל.**
5. **בדיקת עשן עם מפתח אמיתי:** `GET https://v3.football.api-sports.io/status` דרך `ApiFootballAdapter.smoke()` (מוצג במסך הבריאות אחרי הריצה הראשונה של discover) ומשיכה אחת של `/fixtures` ליום — אימות מקור, תאריך וכיסוי לפני הפעלת התזמון.

| אחסון | `lib/pilot30/store/{supabase,memory}.js` + `supabase/migrations/0001_pilot30.sql` |

החלטות מימוש:
- **טכנולוגיה קיימת נשמרה** (JavaScript, לא TypeScript; Supabase ולא Postgres נפרד; GitHub Actions כ-scheduler כמו שאר הפרויקט).
- **פונט:** Heebo המקומי שכבר קיים בריפו (רישיון OFL) במקום DejaVu שבחבילה — כפי שהחבילה מתירה. שבירת השורות נבדקה ב-320/390/768/1440.
- **כסף ויחסים:** אגורות כ-integer; יחסים כ-BigInt בסקלה 1e6; מכפלה ובדיקת מינימום מדויקות לפני כל עיגול (`lib/pilot30/money.js`).
- **מנוע שילובים:** חיפוש מוגבל (iterative deepening על מספר הבחירות, קבוצות מינימליות בלבד, גיזום לפי חסם עליון), עד בחירה אחת למשחק, מפעיל אחד לטופס, תקרה 8 בחירות (ניתנת להגדרה). אין הוספת בחירות כדי להשלים יחס: אם אין שילוב → `no_candidate`.
- **נעילה ותקציב:** פונקציית SQL `p30_commit_ticket` (row lock + אינדקס ייחודי חלקי) מבטיחה טופס אחד ביום וחיוב יחיד גם בלחיצה כפולה או שתי ריצות; במצב demo אותה סמנטיקה עם mutex בזיכרון (נבדק בבדיקות).
- **settlement:** לפי תוצאת 90 דקות + זמן פציעות (`score.fulltime` של API-Football). נדחה/בוטל/הופסק → `pending_review` והכרעה ידנית מתועדת. אין הנחת יחס 1.
- **מודל:** פואסון ניסיוני (`poisson-td-0.1-experimental`) עם עוצמת התקפה/הגנה, יתרון בית ומשקל זמן; מדגם קטן → `null`. בדיקה כרונולוגית (Brier, log loss, כיול) דרך `POST /api/pilot30/model/evaluate`. **אין backtest רווחיות** — אין snapshots של יחסים היסטוריים. ברירת המחדל לדירוג היא חשבונאית בלבד, ללא תווית "מומלץ".

## טבלת חיבורים — עובד לעומת חסר

| שירות | מצב | מה נדרש |
|---|---|---|
| API-Football (API-Sports ישיר) | **מתאם מוכן, contract tests ירוקים; לא בוצעה קריאה חיה** | `API_FOOTBALL_KEY`. גילוי ליגות/עונות בזמן ריצה (ללא מזהים מהזיכרון). לאחר הזנת המפתח: ריצת `discover` אחת ובדיקת `smoke()` |
| יחסי ווינר | **unavailable** (ראה בדיקת ההיתכנות במסך "בריאות המערכת") | לא נמצא מפעיל מזוהה בשום ספק API מתועד; אין endpoint מאומת. `WinnerOddsProvider` קיים כממשק וחוסם הרכבת "טופס ווינר". דרושה החלטה: להמשיך לחפש מקור, או להתחיל פיילוט **market-paper** עם מפעיל בינלאומי (בחירה מפורשת בהגדרות) |
| The Odds API | **מתאם מוכן, contract tests ירוקים; לא בוצעה קריאה חיה** | `ODDS_API_KEY` רק אם נבחר market-paper. גילוי sport keys דרך `/v4/sports`; התאמת אירועים למשחקים לפי ליגה+קבוצות+שעה; התאמה עמומה נעצרת לבדיקה |
| PostgreSQL + Auth (Supabase) | **migration + store מוכנים; לא הורץ מול פרויקט אמיתי** | פרויקט Supabase, הרצת המיגרציה, `SUPABASE_SERVICE_ROLE_KEY`, `OWNER_USER_ID`, כיבוי הרשמה פתוחה |
| Scheduler | **workflow + routes מוכנים; לא הופעל** | `CRON_SECRET` כ-repository secret ו-env var; אופציונלי `PILOT30_BASE_URL` |
| מודל שפה | לא מיושם (אופציונלי) | — |

## עלויות צפויות לפי ספק (הערכה, לאימות מול המחירונים העדכניים)

| ספק | שימוש מתוכנן | תקציב קריאות | הערכת עלות |
|---|---|---|---|
| API-Football | discover יומי (5 ליגות × fixtures), היסטוריה (5 × עונה, cache 24h), הרכבים (≤ 8 משחקים × 2 בדיקות), תוצאות (≤ 8 × ~3 ניסיונות), status | ~40–80 קריאות/יום בממוצע | חבילת החינם (100/יום) מספיקה לרוב הימים; בימי עומס Pro (~19 $/חודש, 7,500/יום). המכסה נשמרת מכותרות `x-ratelimit-*` ומוצגת במסך הבריאות |
| The Odds API | רק ב-market-paper: ~4–6 קריאות ליום (sport odds × ליגות עם משחקים) | ~150/חודש | חינם עד 500 קרדיטים/חודש (שוקי h2h/totals/btts עולים קרדיט לכל שוק־אזור); מעבר לכך ~30 $/חודש |
| Supabase | Auth + Postgres קטן | — | חינם (Free tier) לפרויקט יחיד |
| Vercel / GitHub Actions | ריצות cron קצרות | ~20 ריצות/יום | בתוך המכסות הקיימות של הפרויקט |

העלויות מוזנות בהגדרות (`apiCostMinorPerMonth`) ומוצגות במסך המעקב בנפרד מרווח הטפסים, כולל "תוצאה אחרי הוצאות תפעול".

## מה לבקש מוויטלי (רק עכשיו, כשהקוד מוכן לחיבור)

1. מפתח API-Football (או ספק חלופי עם כיסוי מוכח לחמש הליגות) — להזין כ-`API_FOOTBALL_KEY` ב-Vercel.
2. פרויקט Supabase לפיילוט: URL, anon key, service-role key, ומשתמש בעלים (`OWNER_USER_ID`).
3. החלטה על יחסי ווינר: אין מקור מאומת. להתחיל market-paper עם The Odds API ומפעיל מזוהה? אם כן — `ODDS_API_KEY` ושם המפעיל.
4. תאריך תחילת הפיילוט ומצב (paper / manual-real) — נקבעים במסך ההגדרות ונועלים את הפיילוט.
5. `CRON_SECRET` כ-repository secret ב-GitHub (אותו ערך כמו ב-Vercel) כדי להפעיל את התזמון.

אין לרכוש שירות או להפעיל מנוי בתשלום בלי אישור. מפתח LLM אינו נחוץ ל-MVP.
